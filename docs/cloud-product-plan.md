# Hosted Event CRM implementation plan

## Product boundary

One small Cloudflare Workers application extends this independent repository without changing the Python toolkit or any existing customer deployment. The public website offers a synthetic interactive demo and a guided private workspace setup. It does not publish attendee data. One workspace contains one event, multiple separately scoped audience views, and a named team.

Luma setup takes a calendar API key and canonical event link. The application resolves the event using only Luma's documented calendar/event API, requires manage access, and shows the exact event for confirmation. Luma Plus and calendar-admin authorization are required. Only GET requests go to the fixed API origin, without credential redirects. Provider credentials are encrypted with a Cloudflare secret using authenticated encryption and workspace-bound associated data.

The hosted first release supports Luma only. Partiful is deferred; do not build or advertise a working Partiful login, browser companion or continuous Partiful sync in this release. The existing offline Partiful toolkit remains unchanged. A future integration requires a separately scoped decision about supported host access; never collect a Partiful password or session cookie or imitate an OAuth flow.

## User flow

1. Try the fictional demo, or create a private workspace with host/data-use authorization. Save the owner and separate backup key before connecting Luma.
2. Confirm the matched event, choose professional signup questions, identify company/title/LinkedIn mappings, and exclude hosts/cohosts. No contact or sensitive answers enter storage. Review host identities instead of excluding same-name people automatically.
3. Set the audience's ICP description and explicit answer-value priorities. Add sponsors as distinct audience views with their own rules and question allowlists. Rankings are explainable fit heuristics; checked-in people come first within the configured priority groups. Hosts can instead choose value-first ranking. Missing evidence stays unknown. No third-party enrichment runs in attendance polling.
4. Preview the initial complete roster and confirm the cohort, named team, monitoring window, and retention date. Future new registrations require explicit roster review; changes never silently replace frozen identities or assignments.
5. Invite named teammates and sponsor viewers using independent revocable scoped keys. The event link alone grants no data access. Login exchanges an access key in a POST body for an HttpOnly, Secure, SameSite=Strict session cookie. Keys are stored hashed, never in URLs or localStorage. This is capability-based access, not verified email identity; there is no email sender or password-reset service.
6. Open the dashboard on desktop or phone: audience, search, answer, attendance and owner filters; explainable prioritization; shared assignment/status with optimistic concurrency. Sponsor scopes are enforced on the server, not merely by hiding UI controls. Owners can stop/resume monitoring, revoke keys, export permitted data and delete the workspace.

## Small architecture

- `cloud/`: dependency-light Worker, static HTML/CSS/JS, provider normalization, domain logic, tests and deployment configuration. Existing offline toolkit remains unchanged.
- A small control Durable Object bounds creation/login attempts and tracks valid workspace identifiers. Each workspace has its own SQLite-backed Durable Object for configuration, encrypted credentials, frozen roster, complete attendance revisions, assignments, access-key hashes and session hashes. No public object-storage bucket or second database.
- One alarm per workspace schedules bounded scans. A persisted scan generation/lease prevents overlapping manual and alarm scans. Page cursors and sanitized staging rows can resume in bounded chunks; no partial scan becomes visible. Limits on pages, guests, answers, request sizes, deadlines and scan duration keep resource use bounded. There are no unbounded in-request loops.
- Compare authoritative event binding, question definitions, counts, duplicate identities and exact frozen identity set before publishing a complete revision. Read only explicit ticket check-ins; ambiguous/group-ticket state stays unknown at initial import and cannot erase a previous good update. Permit one fresh retry for a changing source. Unauthorized access pauses with a reconnect action; transient errors use bounded exponential backoff and Retry-After. Alarms explicitly reschedule failures rather than relying only on platform retry counts.
- Persist last-good data independently of the poller's lifetime. Stopped, ended or failed polling leaves the dashboard readable with source timestamps and an honest status. No TTL discards attendance merely because it is stale. A separately chosen retention deadline deletes the workspace's private state. Disconnecting removes the provider key but leaves retained results.
- Fixed origins, no arbitrary remote image proxy, no hidden provider endpoints, no raw response/error logging. Validate API boundaries; escape untrusted display text; CSP, no-store private responses, origin checks for mutations, session expiration, revocation, rate limits and per-workspace isolation. Enforce limits before storage/network operations. No analytics or external UI assets.

## Automatic research and spending

Automatic professional research is required for launch, not a manual operator task. The host provides their business website and each sponsor's website, approves the purpose and selected professional questions, and authorizes professional enrichment. A bounded pipeline researches those websites, proposes evidence-backed ICP rules, locates attendee professional profiles, extracts company/experience evidence and searches for correctly attributed portraits. Results distinguish corroborated identities from candidates, unavailable sources and unresolved matches. No generated faces, face matching, guessed email addresses or confidence percentages presented as proof. Rankings use the scoped registration fields and host-approved rules; research never silently changes those rules. Source material is untrusted data, never executable instructions.

Use existing authorized service keys in Worker secrets, never customer-side code or Git. Favor prepaid search plus a tightly bounded structured-output model; add another provider only when its published pricing and request bounds are known. Reuse findings within the same authorized workspace; no cross-customer sharing of private attendee information. Enrichment runs once per immutable identity/research version, separately from attendance scans, and records provenance and explicit unresolved outcomes. A provider failure triggers a bounded alternative source search, not an invented claim that a person has no photo. The dashboard remains usable during or after incomplete enrichment.

The authorized monthly limits are $50 for Cloudflare and $100 for the entire project. A shared transactional ledger reserves conservative worst-case cost before each external call, including retries, and does not refund an ambiguous timed-out charge. Set a lower application service ceiling to leave operational headroom. Global and per-workspace limits prevent one customer or parallel jobs from consuming the pool. Stop admission and metered work when the budget cannot be safely reserved; show a clear budget-paused state while retaining completed data. Provider billing settings, fixed charges and other users of shared keys are separate from this ledger: never claim an application estimate is a provider-enforced hard account cap. Verify prepaid credit/auto-recharge settings before relying on credit-only spending. Prefer a free-tier Cloudflare deployment with hard service limits; do not upgrade a shared account merely to launch this app.
